# 01. JVM Internals

> Setup: Java 21 (LTS), HotSpot JVM, Spring Boot 3.x, Maven, IntelliJ IDEA.
> Sub-parts: 1.1A Architecture & Class Loading · 1.1B Runtime Data Areas · 1.1C Garbage Collection · 1.1D Execution Engine & JIT

---

## Overview

The JVM is a **specification** (JVMS) plus an **implementation** (HotSpot is the default in OpenJDK, Oracle JDK, Temurin, Corretto). It executes **bytecode**, not Java source, which gives "compile once, run anywhere", managed memory (GC), bytecode verification, and runtime optimisation (JIT).

```
 Hello.java ──javac──► Hello.class (bytecode)
                            │
          ┌─────────────────▼──────────────────┐
          │                JVM                 │
          │  CLASS LOADER SUBSYSTEM            │  Load → Link → Initialize
          │  RUNTIME DATA AREAS                │  Heap | Metaspace | Stacks | PC | Code cache
          │  EXECUTION ENGINE                  │  Interpreter | JIT (C1, C2) | GC
          │  JNI ↔ native libraries            │
          └────────────────────────────────────┘
```

**JDK vs JRE vs JVM (Java 11+):** JDK = tools (`javac`, `jar`, `jcmd`, `jstack`, `jlink`) + runtime. JVM = engine that runs bytecode. A separate JRE is no longer shipped; build trimmed runtimes with `jlink`.

**Why it matters in production:** every `OutOfMemoryError`, `StackOverflowError`, GC pause, slow startup and "works on my machine" classpath bug traces back to one of these subsystems.

## Core Concepts (with internals)

### 1. Class Loading

Classes are loaded **lazily** (on first use).

```
LOADING ──► LINKING (Verify → Prepare → Resolve) ──► INITIALIZATION
```

| Phase | What happens |
|---|---|
| Loading | Find bytes (jar, dir, generated). Metadata → **Metaspace**; `java.lang.Class` object → **heap** |
| Verification | Bytecode verifier checks type safety, stack consistency (`VerifyError`) |
| Preparation | Static fields allocated with **default values** (0/null/false). Compile-time constants get their real value here |
| Resolution | Symbolic refs → direct refs (lazy in HotSpot) |
| Initialization | Run `<clinit>`: static assignments + `static {}` blocks in **textual order**, parent first, **exactly once, thread-safe** (per-class init lock) |

**Initialization triggers ("active use"):** `new`, static method call, read/write of a non-constant static field, `Class.forName()` (initialize=true), subclass initialization (parent first), main class.

**No initialization ("passive use"):** reading a compile-time constant (inlined), `new Foo[10]`, `Foo.class`, `ClassLoader.loadClass()`, `Child.parentStaticField` (only Parent initializes).

Compile-time constant = `static final` primitive or `String` with a constant expression. `static final Integer X = 5` or `static final String S = compute()` are **not** constants.

**Class loader hierarchy (Java 9+):**
```
Bootstrap (native, returns null)   → java.base (java.lang, java.util ...)
   ▼
Platform (was Extension in Java 8) → java.sql, java.xml ...
   ▼
Application / System               → classpath: your code + Maven deps
   ▼
Custom (Spring Boot launcher, Tomcat, DevTools restart loader, plugins)
```

**Parent-delegation:** check cache → ask parent → only then load yourself. Gives **security** (can't replace `java.lang.String`; `java.*` from a custom loader → `SecurityException: Prohibited package name`) and **consistency** (one definition of core classes).

**Class identity = fully qualified name + defining ClassLoader.** Same bytes via two loaders = two types → `ClassCastException: User cannot be cast to User` (e.g., Spring DevTools).

Tomcat uses **child-first** for web apps so each WAR can bundle its own library versions.

### 2. Runtime Data Areas

```
SHARED     : Heap | Metaspace | Code Cache   (+ Direct/off-heap memory)
PER THREAD : PC register | JVM Stack | Native Method Stack
```

**PC register** — address of the current bytecode instruction (undefined in native methods).

**JVM stack** — one **frame** per method call:
```
┌──── Frame ─────────────────────────────────────┐
│ Local Variable Array  [0]=this [1]=a [2]=b ... │  long/double take 2 slots
│ Operand Stack         working area for bytecode│
│ Frame Data            constant pool ref,       │
│                       return address           │
└────────────────────────────────────────────────┘
```
Frame size is fixed at compile time (`javap -c -v` shows `stack=2, locals=4`). The JVM is a **stack-based machine**. Stack size: `-Xss` (≈1 MB default on 64-bit Linux) → `StackOverflowError`.

**Heap** — all objects and arrays; shared; GC-managed.
```
┌─────── Young Generation ───────┬─── Old Generation ───┐
│ Eden │ Survivor S0 │ Survivor S1│ long-lived objects   │
└────────────────────────────────┴──────────────────────┘
```
- **TLAB:** each thread bump-allocates in its own chunk of Eden → lock-free, ~10 instructions per `new`.
- **Escape analysis:** objects that never escape a method may be scalar-replaced (never allocated on the heap).
- **Static fields** live with the `Class` object on the heap (HotSpot 7/8+). **String pool** is on the heap since Java 7.

**Metaspace (Java 8+)** — class metadata in **native memory**; replaced PermGen (fixed-size, `OOM: PermGen space`). Unbounded by default; freed per ClassLoader. Cap with `-XX:MaxMetaspaceSize`.

**Code cache** — JIT-compiled native code. Full → `CodeCache is full. Compiler has been disabled.`

**Direct memory** — `ByteBuffer.allocateDirect()`, Netty. `-XX:MaxDirectMemorySize`.

**JVM process memory ≈ heap + metaspace + (threads × Xss) + code cache + direct memory + GC structures.**

### 3. Object Memory Layout (64-bit HotSpot, Java 21)

```
┌──────────────────┬──────────────────┬────────┬─────────┐
│ Mark Word (8 B)  │ Klass ptr (4 B)  │ Fields │ Padding │  aligned to 8 bytes
│ hash, GC age,    │ → Metaspace      │        │         │
│ lock state       │                  │        │         │
└──────────────────┴──────────────────┴────────┴─────────┘
Header = 12 bytes (compressed class pointers, default)
```

| Object | Size |
|---|---|
| `new Object()` | 16 B (12 + 4 padding) |
| `Integer` | 16 B |
| `Long` | 24 B (12 + 4 gap for 8-byte alignment + 8) |
| `new int[0]` | 16 B (12 + 4 length) |
| `new int[100]` | 416 B |

- **Compressed oops:** 4-byte references up to ~32 GB heap. `-Xmx33g` can hold fewer objects than `-Xmx31g`.
- **Boxing cost:** 1M `Long` in a `List` ≈ 24 MB + 4 MB refs; `long[1_000_000]` ≈ 8 MB.
- The JVM reorders fields to minimise padding. Inspect with **JOL**.
- Java 24+ has experimental compact (8-byte) headers — not in Java 21.

### 4. Garbage Collection

**Reachability, not reference counting.** Objects reachable from **GC roots** are live; everything else (including cycles) is garbage.

**GC roots:** locals/params in active frames, static fields, live threads, JNI references, objects held as monitors, classes of system loaders.

**Java memory leak** = objects no longer needed but **still reachable** (static collections, unbounded caches, `ThreadLocal` in pooled threads, listeners, mutable `HashMap` keys).

**Algorithms:**
```
Mark-Sweep   : free in place → fragmentation
Mark-Compact : slide live objects together → no gaps, slower
Copying      : copy live to empty space → cost ∝ LIVE objects (ideal for young gen)
```

**Generational hypothesis:** most objects die young.

**Minor GC flow:**
1. `new` → Eden (TLAB)
2. Eden full → minor GC (STW, usually ms)
3. Live objects in Eden + current Survivor → copied to other Survivor, `age++`
4. Age reaches `MaxTenuringThreshold` (default 15; 4 age bits in mark word) → promoted to Old
5. Survivor overflow → **premature promotion**
6. Old fills → major / mixed / full GC

**Card table + write barrier:** Old is split into 512-byte cards; storing a reference marks the card dirty; minor GC scans only dirty cards for Old→Young references (G1: per-region **remembered sets**).

**Stop-the-world & safepoints:** threads pause at safepoints (method returns, loop back-edges) so the GC can work on a stable graph.

**Concurrent marking — tri-color:** white (unvisited) / grey (visited, children pending) / black (done). Mutator could hide a white object behind a black one → barriers fix it (G1: SATB write barrier; ZGC: load barriers + colored pointers).

**Collectors (Java 21):**

| Collector | Flag | Pauses | Use for |
|---|---|---|---|
| Serial | `-XX:+UseSerialGC` | Long | Tiny heaps; **auto-selected if < 2 CPUs or < ~1792 MB** |
| Parallel | `-XX:+UseParallelGC` | 100 ms – s | Throughput / batch (default in Java 8) |
| **G1** | default since Java 9 | Target 200 ms | Most Spring Boot services |
| ZGC | `-XX:+UseZGC -XX:+ZGenerational` | < 1 ms, any heap size | Low latency / huge heaps |
| Shenandoah | `-XX:+UseShenandoahGC` | < 10 ms | Not in Oracle JDK |
| Epsilon | `-XX:+UseEpsilonGC` | none (never collects) | Benchmarks |

CMS: deprecated in 9, **removed in 14**. Generational ZGC is opt-in in 21, default from 23, the only mode from 24.

**G1:** heap split into ~2048 regions (E/S/O/Humongous/Free). Young GC evacuates Eden + Survivor. Concurrent marking starts at ~45% Old occupancy (IHOP). **Mixed GC** evacuates Old regions with most garbage first ("Garbage-First"). `-XX:MaxGCPauseMillis=200` is a goal. **Humongous** = object ≥ 50% of region size. **Full GC in G1 logs = red flag** (evacuation failure).

**ZGC:** colored pointers + self-healing load barriers → objects relocated concurrently; pauses only scan thread stacks → < 1 ms regardless of heap size. Costs a few % throughput and needs headroom.

**Reference types:** Strong (never collected while reachable) > Soft (collected under memory pressure) > Weak (next GC; `WeakHashMap`) > Phantom (`get()` always null; `Cleaner`). `finalize()` is **deprecated for removal** (Java 18, JEP 421).

### 5. Execution Engine & JIT

**Interpreter** runs bytecode immediately and collects **profiles** (invocation/loop counts, branch directions, receiver types). **JIT** compiles hot code to native code in the **code cache** on background threads.

**Tiered compilation (default since Java 8):**

| Tier | What |
|---|---|
| 0 | Interpreter + profiling |
| 1 | C1, no profiling (trivial methods) |
| 2 | C1, limited profiling (C2 queue busy) |
| 3 | C1, full profiling |
| 4 | C2, full optimisation |

Typical path **0 → 3 → 4** (`Tier3InvocationThreshold=200`, `Tier4InvocationThreshold=5000`, approximately; loop iterations count too).

**OSR (On-Stack Replacement):** back-edge counters trigger compilation of a hot loop; the running frame switches to compiled code mid-loop (`%` in `PrintCompilation`).

**C2 optimisations:**
- **Inlining** (< 35 B bytecode; hot < 325 B) — enables everything else
- **Devirtualization:** monomorphic / bimorphic call sites inlined behind type guards; **megamorphic (3+ types) → real vtable call**; CHA inlines when only one implementation is loaded
- Escape analysis → scalar replacement, **lock elision**
- Range-check elimination, implicit null checks, loop unrolling, vectorization
- Constant folding, **dead code elimination**
- **Intrinsics:** `System.arraycopy`, `Math.*`, `String.equals`, CRC32, AES

**Speculation & deoptimization:** C2 compiles assumptions (type seen, branch never taken). Violation → uncommon trap → method **"made not entrant"** → back to interpreter → re-profile → recompile. Repeated cycles = deopt storm.

**Startup options:**

| Approach | Startup | Peak | Trade-off |
|---|---|---|---|
| Normal JIT | Slow | Best | Warm-up |
| CDS / AppCDS (Boot 3.3+) | 20–40% faster | Same | Archive built at build time |
| GraalVM Native Image | ms, low RSS | Often lower | Long builds; reflection hints |
| CRaC | ms, already warm | Best | Supported JDKs only (Azul, Liberica) |

Project Leyden brings AOT features into the JDK from Java 24.

### Common leaks and fixes
```java
// LEAK: unbounded static cache
private static final Map<String, Report> CACHE = new HashMap<>();
// FIX: bounded cache with eviction, e.g. Caffeine
// Caffeine.newBuilder().maximumSize(10_000).expireAfterWrite(Duration.ofMinutes(10)).build();

// LEAK: ThreadLocal in a thread pool (also a data-leak/security bug)

    private static final ThreadLocal<UserSession> CTX = new ThreadLocal<>();
    public static void set(UserSession s) { CTX.set(s); }
    public static UserSession get()       { return CTX.get(); }
    public static void clear()            { CTX.remove(); }
}

public void handle(Request req) {
    UserContext.set(loadSession(req));
    try {
        process(req);
    } finally {
        UserContext.clear();   // always in finally
    }
}
```

### Deoptimization: mono → bi → megamorphic
```java
interface Shape { double area(); }
record Circle(double r)             implements Shape { public double area() { return Math.PI * r * r; } }
record Square(double s)             implements Shape { public double area() { return s * s; } }
record Triangle(double b, double h) implements Shape { public double area() { return 0.5 * b * h; } }

public class DeoptDemo {
    static double total(Shape s) { return s.area(); }

    public static void main(String[] args) {
        double sum = 0;
        for (int i = 0; i < 5_000_000; i++) sum += total(new Circle(i));
        System.out.println("phase 1: monomorphic");
        for (int i = 0; i < 5_000_000; i++) sum += total(new Square(i));
        System.out.println("phase 2: bimorphic");
        for (int i = 0; i < 5_000_000; i++) sum += total(new Triangle(i, 2));
        System.out.println("phase 3: megamorphic " + sum);
    }
}
```

## Common Pitfalls

**Class loading**
- Logs full of `NoClassDefFoundError: Could not initialize class X` → real cause is the **first** `ExceptionInInitializerError`. Avoid I/O/env reads in static initializers.
- `NoSuchMethodError` / `NoSuchFieldError` → two versions of a library on the classpath. Use `mvn dependency:tree -Dincludes=<group>` + `<dependencyManagement>` / exclusions.
- Constant inlining: a library changes `public static final int TIMEOUT` but clients aren't recompiled → stale value.
- Classloader leaks (redeploys, `ThreadLocal`, static caches, JDBC drivers in `DriverManager`) → `OOM: Metaspace`.
- Circular static initialization across threads → silent class-init **deadlock**.
- `Class.forName` initializes; `loadClass` doesn't. JDBC 4+ drivers self-register via `ServiceLoader`.

**Memory areas**
- Kubernetes **OOMKilled** while heap is fine → non-heap memory. Use `-XX:MaxRAMPercentage=75`, not `-Xmx` = container limit. Investigate with `-XX:NativeMemoryTracking=summary` + `jcmd <pid> VM.native_memory summary`.
- Error → area → fix:
  ```
  StackOverflowError                 → recursion                → fix code
  OOM: Java heap space               → leak / small heap        → heap dump + MAT
  OOM: GC overhead limit exceeded    → almost all time in GC    → effectively a heap leak
  OOM: Metaspace                     → classloader leak / proxy explosion
  OOM: Direct buffer memory          → NIO/Netty buffers
  OOM: unable to create native thread→ OS thread limit (bigger -Xmx makes it WORSE)
  ```
- Bidirectional JPA entities serialized by Jackson → infinite recursion → `StackOverflowError`.
- 1000 platform threads × 1 MB stacks ≈ 1 GB native memory (motivation for virtual threads).
- Heap > 32 GB disables compressed oops.
- Set `-Xms = -Xmx` on servers; always enable `-XX:+HeapDumpOnOutOfMemoryError`.
- Set `-XX:MaxMetaspaceSize` so leaks fail with a readable error.

**GC**
- Container with < 2 CPUs or < ~1792 MB → JVM silently picks **Serial GC**. Give ≥ 2 CPUs or set `-XX:+UseG1GC`.
- `System.gc()` in code → Full GCs. `-XX:+DisableExplicitGC` (careful with direct buffers).
- Most GC problems are **allocation problems** (loading huge result sets, big JSON strings, boxing, unbounded caches). Fix code before tuning flags.
- G1 humongous allocations (large uploads/reports) → fragmentation, Full GC. Stream instead of buffering, or raise `-XX:G1HeapRegionSize`.
- Mutable `HashMap` keys → entries lost forever → leak.
- Listeners never unregistered.
- `MaxGCPauseMillis` too low → constant GC, throughput collapse. Need < 10 ms? Use ZGC.
- Live set should be ~30–50% of heap after full GC.

**JIT**
- NPEs with no stack trace → `OmitStackTraceInFastThrow`. Find the first occurrence or use `-XX:-OmitStackTraceInFastThrow`.
- Load testing / judging a cold JVM. Warm up; gate readiness probes on warm-up.
- CPU limits starve JIT compiler threads → long warm-up in containers.
- Methods > 8000 bytes of bytecode are never compiled (`DontCompileHugeMethods`).
- Megamorphic call sites in hot loops prevent inlining.
- Exceptions for control flow are expensive (stack trace capture).
- Code cache full → JIT disabled silently. Monitor with `jcmd <pid> Compiler.codecache`.
- Native Image: reflection/proxies/resources must be known at build time; test the native build in CI.
- Never benchmark with `System.nanoTime()` loops — use JMH.

## Interview Questions & Answers

**Q: Explain the class loading process.**
Loading (bytes → Metaspace metadata + `Class` object on heap) → Linking (verify, prepare statics with defaults, resolve references) → Initialization (`<clinit>`, static code in textual order, parent first, once, thread-safe).

**Q: What is parent-delegation and why?**
A loader asks its parent before loading itself. Prevents core classes being replaced (security) and duplicate definitions (consistency).

**Q: Can you create your own `java.lang.String`?**
You can write it, but delegation always returns the bootstrap version; defining `java.*` in a custom loader throws `SecurityException: Prohibited package name`; the module system also rejects it at compile time.

**Q: `ClassNotFoundException` vs `NoClassDefFoundError`?**
CNFE: checked, explicit lookup by name failed. NCDFE: Error, class existed at compile time but is missing or failed to initialize at runtime.

**Q: Same fully qualified name — same type?**
Only if loaded by the same defining ClassLoader.

**Q: Why is the holder singleton thread-safe without `synchronized`?**
The JVM initializes a class exactly once under a lock; the holder is initialized lazily on first access.

**Q: Does accessing a `static final` field always initialize the class?**
No — compile-time constants are inlined. `static final Integer` or computed values do trigger initialization.

**Q: Which runtime areas are shared vs per-thread?**
Shared: heap, Metaspace, code cache. Per-thread: PC register, JVM stack, native method stack.

**Q: What is in a stack frame?**
Local variable array, operand stack, frame data (constant pool reference, return address). Size fixed at compile time.

**Q: Where do locals, objects and statics live?**
Primitive locals and references in the stack frame; objects on the heap; statics on the heap with the `Class` object (HotSpot 8+); metadata in Metaspace.

**Q: Why was PermGen replaced by Metaspace?**
PermGen was fixed-size and hard to tune (`OOM: PermGen space`). Metaspace uses native memory, grows automatically, and is freed per classloader.

**Q: Is Java pass-by-value?**
Always. Object parameters receive a copy of the reference.

**Q: Why is object allocation fast?**
TLAB bump-pointer allocation without locks; escape analysis may avoid allocation entirely.

**Q: Size of `new Object()`?**
16 bytes: 12-byte header + 4 bytes padding.

**Q: What are compressed oops?**
32-bit scaled references addressing up to ~32 GB heap; above that references become 64-bit.

**Q: Heap is stable but the pod keeps getting OOMKilled — why?**
Non-heap memory (Metaspace, thread stacks, direct buffers, code cache) exceeds the container limit. Use `MaxRAMPercentage` and Native Memory Tracking.

**Q: How does the JVM decide what is garbage?**
Tracing from GC roots; unreachable objects (including cycles) are garbage.

**Q: Explain minor GC and the generational hypothesis.**
Most objects die young. Eden → survivors copied between S0/S1 with age++ → promoted to Old at the threshold. Copying cost is proportional to survivors, so it's fast.

**Q: How are Old→Young references found without scanning Old?**
Write barrier + card table (G1: remembered sets).

**Q: What are STW pauses and safepoints?**
All application threads stopped at known-consistent points so the GC can safely operate.

**Q: G1 vs ZGC?**
G1: regions, concurrent marking, STW evacuation, 200 ms soft target, the default. ZGC: concurrent relocation via colored pointers + load barriers, < 1 ms pauses at any heap size, slightly lower throughput.

**Q: Can Java leak memory?**
Yes — unneeded but reachable objects: static collections, unbounded caches, `ThreadLocal` in pools, listeners, mutable map keys.

**Q: Reference types?**
Strong, Soft (low memory), Weak (next GC), Phantom (post-mortem cleanup via queue/`Cleaner`). `finalize()` deprecated for removal.

**Q: API has periodic 1–2 s latency spikes — how to investigate?**
GC logs for Full GC / long pauses → `jstat` Old Gen trend → heap dump + MAT if growing → check humongous allocations and selected collector → fix allocations, then tune or switch to ZGC.

**Q: Is Java compiled or interpreted?**
Both: `javac` → bytecode; JVM interprets, then JIT-compiles hot code.

**Q: Why can JIT beat AOT?**
It uses real runtime profiles for speculative optimisation (inlining actual receiver types, pruning untaken branches) and can deoptimize if assumptions fail.

**Q: Explain tiered compilation.**
Tier 0 interpreter → tier 3 C1 with profiling → tier 4 C2 optimized. Fast warm-up plus peak performance.

**Q: What is OSR?**
Compiling a hot loop and switching the running frame to compiled code mid-execution.

**Q: What is deoptimization?**
Invalidating compiled code when a speculative assumption breaks, returning to the interpreter, re-profiling and recompiling.

**Q: Mono/bi/megamorphic?**
Number of receiver types at a call site; 1–2 → inlined behind guards; 3+ → vtable call.

**Q: Why not benchmark with `nanoTime` loops?**
No warm-up, dead code elimination, OSR distortion, GC noise. Use JMH.

**Q: NPEs without stack traces in logs?**
`OmitStackTraceInFastThrow` — C2 uses preallocated exceptions after repeated throws. Find the first occurrence or disable the flag.

**Q: How to reduce Spring Boot startup time?**
AppCDS (Boot 3.3+), lazy init where safe, trimming auto-configuration, GraalVM Native Image, CRaC.

## Quick Revision

- JVM = spec + implementation (HotSpot); runs bytecode.
- Class loading = Load → Verify → Prepare → Resolve → Initialize.
- Prepare sets defaults; `<clinit>` sets real values (except compile-time constants).
- `<clinit>` runs once, thread-safe, parent first → holder singleton.
- Constants, arrays, `.class`, `loadClass()` don't initialize a class.
- Loaders: Bootstrap (null) → Platform → Application → Custom; parent-first.
- Class identity = FQN + defining ClassLoader.
- CNFE = explicit lookup failed; NCDFE = missing/broken at runtime; failed init → EIIE once, NCDFE forever.
- Shared: heap, Metaspace, code cache. Per-thread: PC, JVM stack, native stack.
- Stack frame = locals + operand stack + frame data; JVM is stack-based.
- TLAB = lock-free bump allocation; escape analysis may skip heap allocation.
- Statics and String pool live on the heap (HotSpot 7/8+).
- Metaspace = native memory, replaced PermGen, freed per ClassLoader.
- Object header = 12 B; `Object` 16 B, `Integer` 16 B, `Long` 24 B.
- Compressed oops up to ~32 GB heap.
- Java is always pass-by-value.
- JVM memory = heap + metaspace + threads×Xss + code cache + direct + GC.
- GC = reachability from roots; cycles collected; leaks = still reachable.
- Young: Eden → Survivor (age++) → Old at age 15; copying cost ∝ survivors.
- Card table + write barrier handle Old→Young refs.
- STW pauses happen at safepoints; concurrent GCs use tri-color + barriers.
- G1 default since 9; regions; 200 ms target; humongous ≥ 50% region; Full GC = red flag.
- ZGC < 1 ms pauses; Java 21 needs `-XX:+ZGenerational`.
- < 2 CPUs or < ~1792 MB → Serial GC auto-selected.
- CMS removed in Java 14; `finalize()` deprecated for removal.
- Fix allocation patterns before tuning GC.
- Tiered: 0 interpreter → 3 C1 profiling → 4 C2.
- OSR compiles hot loops mid-execution (`%`).
- Inlining is the key optimisation; megamorphic (3+ types) blocks it.
- Speculation + deopt → "made not entrant".
- Methods > 8000 bytecode bytes never JIT-compiled.
- No-trace NPEs = `OmitStackTraceInFastThrow`.
- Benchmark only with JMH.
- Startup: AppCDS, Native Image, CRaC.
- Essential prod flags: `-Xms=-Xmx` or `MaxRAMPercentage`, `HeapDumpOnOutOfMemoryError`, `-Xlog:gc*` with rotation.
